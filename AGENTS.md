# StudSync agent instructions

StudSync is a native Swift/SwiftUI menu-bar app for Universität Göttingen Stud.IP files in ordinary Finder folders. Personal Apple Silicon use comes first.

## Development

- Use Ponytail: make the smallest complete change, reuse existing code and platform APIs, and avoid speculative abstractions.
- Use the Build macOS Apps skills for native work and GitHub tools or `gh` for repository operations.
- Read `SECURITY.md` for authentication, networking, files, persistence, and workflow changes.
- Build/run when requested: `./script/build_and_run.sh`. Run automated tests, package checks and CodeQL in GitHub Actions after review; do not run local verification or CodeQL. Keep the existing test tooling for CI.
- Keep networking/sync in StudSyncCore and presentation in StudSyncApp. Keep the app and its build/test tooling native; do not invoke an external interpreter.
- Add focused regression tests for nontrivial changes; keep existing checks passing.
- Never use OpenAI API credentials or API-billed Codex Actions. Use the owner's ChatGPT subscription; GitHub CI runs conventional tools only.
- Follow `docs/ROADMAP.md`. Continue the highest-priority unfinished task, add relevant regression coverage, and create/update a focused PR against `master`. Multiple development PRs may remain open. Put independent changes in separate branches and focused PRs; coordinate overlapping changes rather than implementing the same feature twice. Follow the automatic developer cycle below when asked to start the developer.
- Maintain `docs/ROADMAP.md` in every PR: record implemented work, remaining gaps, and relevant verification; distinguish work in an open PR from merged work. Before starting the next task, reconcile the roadmap with merged/open PRs and the code so completed or in-progress features are not implemented twice. After a PR closes, reconcile its outcome in the next development update; revert completion claims for reverted or abandoned work.
- Use the owner-installed CodeRabbit integration; the owner is disabling the Codex review bot. Codex remains the development agent, not a required PR reviewer. Do not create another reviewer, security schedule, custom status publisher, or merge bot.
- Batch related roadmap changes and push complete batches for CodeRabbit review, then let GitHub Actions verify the reviewed head. Independent changes still need separate branches when bundling would obscure their review. Known Markdown-only changes skip native builds and CodeQL through the shared change-scope job; never bypass checks for executable, resource, dependency or workflow changes.
- After reviewed app/runtime-dependency changes merge and master passes CI, publish the next appropriate app version under `docs/RELEASING.md`. Documentation-only changes need no release. Verify the hosted archive and signed feed; if build/signing/publication fails, keep any draft unpublished and report the blocker.

## Roadmap reconciliation and ownership

Before choosing a roadmap task, and again after merging a PR:

1. Refresh remote refs with `git fetch --prune origin` and read `origin/master:docs/ROADMAP.md` as the merged baseline. A checked-out branch's roadmap can be older or contain unmerged claims; never use it alone.
2. Overlay open PRs by inspecting their descriptions, changed files and relevant diffs/code. Match actual scope to roadmap items. An open implementation reserves its scope: continue that PR or choose independent work instead of duplicating it.
3. List local/remote branches and worktrees. For plausible overlapping work without an open PR, inspect its diff, uncommitted work and handoff, and check merged/closed PR history. A branch name alone proves neither active work nor completion; old branches can survive squash merges. Do not overwrite or discard work to resolve uncertainty. Record the uncertainty and defer overlapping work while continuing independent tasks.
4. Record each queued item's status as **Planned**, **In progress**, or **Merged**, with its PR link or, before a PR exists, its branch/worktree and next step. Mark only surviving merged scope as Merged; keep unimplemented portions Planned. Reconcile reverted/abandoned work with the actual code before reopening it.
5. Reconcile roadmap conflicts from that baseline, PR outcomes and code rather than blindly combining checkboxes from different branches. Update the roadmap in the focused PR. If remote/PR information is unavailable, report the missing evidence and do not assume an overlapping task is free.

## Automatic developer cycle

When instructed to start the automatic developer, execute this cycle in the current run; do not create or change a schedule unless explicitly requested.

1. Apply the roadmap reconciliation and ownership procedure above, then reconcile unfinished conversation tasks with that combined state and issues. Continue still-valid unfinished work first; do not recreate completed or abandoned work. Critical correctness/security failures take priority over features. Record blockers and continue independent work rather than letting a blocked task stall the entire run.
2. Inspect existing PRs for failed checks, conflicts, and unhandled CodeRabbit feedback and any surviving historical review findings, including review summaries. Evaluate suggestions using the connected code, tests, and product scope. Accept useful findings with fixes and regression coverage (verified by post-review CI), or reject unsuitable suggestions with a concrete reason in their conversations. Coordinate with an active CodeRabbit autofix task before editing overlapping files; fetch its commits before pushing.
3. Monitor reviews/CI and enable GitHub auto-merge only after the current head meets the rules below, including for PRs updated in this run. After a confirmed merge, delete its branch only if no other PR, worktree, or unfinished work depends on it. Reconcile remaining PRs with changed master; updated heads need fresh review/checks.
4. Address issues and maintenance needs, prioritizing bugs, security/Dependabot findings, regressions, and CI failures. Check for an existing implementation or PR before starting another fix.
5. Develop the next clearly scoped unfinished roadmap item, add relevant regression coverage, and create/update a focused PR. Continue with additional independently actionable items on their own branches. Do not start overlapping implementations or duplicate work already in open PRs.
6. Maintain the roadmap and affected documentation in each PR, recording implementation, verification, open-PR versus merged status, blockers, and next steps. Save reviewable progress so another run can resume without reconstructing the conversation.
7. Repeat from step 1 while useful actionable work and sufficient allowance remain. Stay with active review/CI runs, work on independent items meanwhile, and check at bounded intervals rather than busy-polling. Handle findings, push and await fresh review followed by GitHub checks until an eligible PR can merge. Stop for required owner input, persistent service/authentication failures, or a usage limit; preserve a clean handoff. Do not create no-op pushes or invent work to consume allowance. When the roadmap is complete, maintain existing functionality and act on concrete findings rather than inventing features.

Do not overlap developer runs in the same checkout or branch. Check ownership before editing and coordinate/defer conflicting work. Multiple open PRs do not authorize simultaneous conflicting writes.

## Review decisions and merging

- Review comments are suggestions, not mandatory changes. Decide independently whether each improves correctness, security, or intended behavior. Record a fix with regression coverage committed/pushed to the PR or a concrete rejection reason before resolving its conversation. Resolve handled findings so review can finish; post-review CI must verify fixes before merge. Never weaken tests or security controls to hide a failure.
- Enable GitHub auto-merge only when CodeRabbit has completed review and approved the current head without outstanding feedback, the required Change scope/native/CodeQL/CodeRabbit checks pass, and all required conversations are resolved. Inspect the current-head review and feedback; skipped, rate-limited, stale or failed reviews do not qualify. No Codex review or reaction is required. PR CI starts on review submission/dismissal: Change scope fails closed until the latest CodeRabbit decision approves that head and every review thread is resolved; expensive jobs run only after that gate succeeds. A new head needs fresh review and CI. Master pushes and the existing weekly scan retain CI.
- Recheck that the head has not changed and GitHub reports the PR immediately mergeable with every requirement satisfied, then use `gh pr merge --auto --squash --match-head-commit <reviewed-sha>` or the connected equivalent. The SHA argument constrains the request when issued; it is not a persistent head lock on deferred auto-merge. If GitHub queues auto-merge instead of merging immediately, disable that request and keep monitoring. Never leave a deferred request that could merge a later, unreviewed head. PRs created/updated in this run may merge once these conditions pass. Confirm the merge before tagging releases or deleting branches. Never use `--admin`, force-push, bypass protections, or ask a bot to approve/resolve findings without handling them.
- Disable queued auto-merge before any push, branch update or additional work. A new SHA requires fresh reviews/checks; resolved older conversations and older approvals are insufficient. Keep watching until merge or a concrete blocker; cancel auto-merge if the head or review eligibility changes. Verify the actual current-head CodeRabbit review as well as check statuses before enabling auto-merge.
- Notify only meaningful completion, persistent failure, or required owner input; stay quiet on unchanged/non-actionable state.

These instructions authorize actions but do not grant platform capabilities. Development agents can handle feedback when the hosted reviewer cannot edit, push, or merge. Report unavailable authentication/tools or required owner input rather than creating no-op pushes. Do not claim success without evidence. Keep credentials and private vulnerability details out of public comments. GitHub review decisions and merging are distinct; authors cannot formally approve their own PRs.

If the final review thread is resolved after CodeRabbit has already approved the current head, rerun that head's failed `pull_request_review` CI run with GitHub's Re-run all jobs action or `gh run rerun <run-id>`. Resolving a thread does not emit a review-submitted event. The developer must check this transition while handling feedback, verify the run belongs to the current head, and rerun the existing gated workflow; do not push an empty commit or bypass the gate. Rerunning rechecks approval, live head/base and all threads.
